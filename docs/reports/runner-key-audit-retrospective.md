# 필수 체크 무력화 3연속 사이클 회고 — 2026-08-10

## 1. 개요

`main`의 필수 상태 체크는 정확히 둘이다: **`Lint`**(`lint.yml`의 `lint-gate`)와
**`Security Scan Gate`**(`security-scan.yml`의 애그리게이터). 이 둘이 통과하면
머지된다. 따라서 "이 둘을 소리 없이 통과시키는 방법"이 이 레포에서 가장 값비싼
결함 클래스다.

2026-08-08부터 2026-08-10까지 그 클래스를 닫아 나갔고, 각 사이클은 **이전
사이클이 남긴 사각지대에서 시작**했다. 4.4·4.5절은 이 회고가 만든 체크리스트를
처음 돌린 감사가 되돌려준 것이다 — 회고가 다음 발견의 도구가 됐다는 뜻이고,
동시에 앞 절들이 완결이 아니었다는 뜻이다.

## 3. 주제 1 — 실행형 증명의 사각지대

### 3.1 실행이 실제로 닫은 것

PR #404 이전의 가드는 `run:` 본문에서 `exit 1`을 텍스트로 찾았다. 세 번 패배했다.

| 시도 | 패배시킨 형태 수 |
|---|---|
| 원본 가드 | 1 — `#` 주석 줄이 스캔 앵커를 자기 안으로 옮김 |
| #402의 수정 | 4 — 인용 문자열, heredoc 본문, YAML 스칼라, 죽은 분기 |
| 줄-앵커 수정 | 6 — + 들여쓴 heredoc 종결자, 한 줄 heredoc 2개, 분할/비단어 구분자 |

근본 원인은 구조적이다. **"앵커가 줄 앞에 있다"는 "앵커가 셸 명령 위치에 있다"의
필요조건일 뿐 충분조건이 아니다.** 게다가 도달가능성 형태(`if false; then`,
도달 불가 `elif`, `case … never) exit 1`)는 어떤 텍스트 매처로도 닿지 않는다.

실행은 이 열거 게임을 끝냈다. CRITICAL 픽스처를 넣고 게이트를 돌려서 프로세스가
non-zero로 끝나는지 보면, **셸이 어떻게 쓰였든** 결과는 하나다. 회피할 표면이 없다.

### 3.2 실행이 구조적으로 못 보는 것

여기가 핵심이다. 실행형 증명의 범위는 **"누가 그 텍스트를 소비하는가"** 로 정확히
결정된다.

| 텍스트 | 소비자 | 실행으로 커버되나 |
|---|---|---|
| `run:` 본문 | **bash** | ✅ 완전히 (프로세스를 돌리면 끝) |
| 스텝 `if:` | **러너** | ❌ 실행된 프로세스는 이 키를 본 적이 없다 |
| 스텝 `continue-on-error:` | **러너** | ❌ 프로세스는 non-zero로 끝나는데 러너가 버린다 |
| 잡 `continue-on-error:` | **러너** | ❌ 잡 결론이 `success`로 바뀐다 |
| 잡 `if:` / `needs:` | **러너** | ❌ 잡이 아예 안 돈다 |

이 표는 전부 스텝을 **건너뛰는** 키다. 건너뛰지 않고 **방향을 바꾸는** 계열이
따로 있다는 것은 이 회고가 만든 체크리스트를 처음 돌렸을 때 드러났다 — 4.4절.

`run:` 본문을 실행하는 하니스는 **정의상** 그 본문 바깥을 볼 수 없다. 스텝이
`if: false`면 그 본문은 애초에 실행되지 않고, `continue-on-error: true`면
`exit 1`이 러너에게 도달하지 못한다. 두 경우 모두 하니스는 여전히 "게이트는
CRITICAL에서 실패한다"고 **참인 사실**을 보고한다. 참인데 무의미하다.

> **실행형 증명은 증명의 경계를 옮긴 것이지 없앤 게 아니다.**
> 무엇을 실행했는지가 아니라 **실행된 것이 무엇을 볼 수 있는지**가 커버리지다.

PR #404는 이걸 알아챘다 — 라운드 2에서 `workflow_level_disables()`를 추가했다.
문제는 그 다음이다.

## 4. 주제 2 — 잘못된 규모 추정이 만든 두 번의 공백

같은 실수가 두 사이클 연속으로, 반대 방향으로 일어났다.

### 4.1 공백 1 — 대상을 너무 작게 잡았다 (#404 → #407)

PR #404의 워크플로 레벨 검사는 **스텝 1개**를 대상으로 했다. 암묵적 전제는
"게이트 = 내가 지금 보고 있는 그 스텝"이었다.

실제 구조는 그렇지 않다. 필수 컨텍스트는 **애그리게이터**이고, 애그리게이터는
`needs:`를 통해 그래프 전체의 결론을 받는다.

```
required contexts        ["Lint", "Security Scan Gate"]
lint-gate                의존 15 + 자기 자신
security-scan-gate       의존  3 + 자기 자신
────────────────────────────────────────────
그래프 전체              20잡
그중 보호되고 있던 것     1스텝
```

20잡 전부가 잡 레벨 `continue-on-error: true` **한 줄**로 `success`를 결론짓고,
두 애그리게이터 모두 모든 의존으로부터 `success`/`skipped`를 받아들인다.
필수 체크 **자기 자신**도 예외가 아니다 — `security-scan-gate`에 잡 레벨
`continue-on-error`를 붙이면 자기 `sys.exit(1)`과 무관하게 success로 끝난다.

실측(실제 파일 변형 → 스위트 실행 → 복원):

```console
security-scan.yml + security-scan-gate에 잡 레벨 continue-on-error
  기존 게이트 가드 4종 (63 tests)   ALL PASSED   <- 구멍은 실재, 미탐지
  #407의 가드                        FAILED

lint.yml + "Dependency Review" 스텝에 continue-on-error
  test_ci_gate_topology + test_ci_required_jobs_exist (15)   ALL PASSED
  #407의 가드                                                 FAILED
```

기존 가드들이 green인 이유가 중요하다. `test_gate_runs_always`는 `if: always()`를,
`test_gate_aggregates_required_needs`는 `needs:` 목록을,
`test_gate_passset_not_loosened`는 패스셋 문자열을 본다. 뮤테이션은 **그 셋 중
무엇도 건드리지 않는다.** 각 가드는 자기가 보는 것에 대해 정확했다.

그래서 #407은 세 군데를 고치는 대신 `DESIRED_CONTEXTS`에서 시작해 `needs:`를
전이적으로 걸었다. 감사가 지목한 3개 사이트만 막았다면 **17잡 + 이후 추가되는
모든 잡**이 열린 채로 남았을 것이다.

### 4.2 공백 2 — 판단 근거를 엉뚱한 모집단에서 잡았다 (#407 내부)

PR #407의 **첫 버전은 스텝 레벨 `if:`를 대상에서 제외했다.** 근거는
"조건부 스텝은 흔하다, 금지하면 오탐 폭탄이 된다"였다.

이 근거는 틀렸고, **논쟁이 아니라 측정으로** 틀렸다. 모집단을 잘못 잡은 것이다 —
"레포의 모든 워크플로"를 기준으로 흔함을 판단했지, **이 가드가 덮는 그래프**를
기준으로 세지 않았다.

```
그래프 내 스텝 수        105
`if:`를 가진 스텝          7   (5개는 bare always(), 2개는 정당)
```

오탐 폭탄이 아니라 허용목록 2줄이었다. 그리고 그 제외가 남긴 구멍은 실측된다:

```console
`Run gitleaks` 스텝 + continue-on-error  -> 가드 FAILED (정상 탐지)
`Run gitleaks` 스텝 + if: false          -> 가드 14/14 통과 (구멍)
```

`Run gitleaks`는 그 잡에서 **실패할 수 있는 유일한 스텝**이다. 건너뛰면 잡은
실패할 거리가 없어져 **기본값으로** `success`가 된다. 잡 레벨 키는 필요 없다.
`Dependency Review`, `pii-check`도 같은 형태다.

> **"흔하다/드물다"는 모집단을 명시하지 않으면 근거가 아니다.**
> 세어보는 데 1분 걸렸고, 결론이 뒤집혔다.

### 4.3 방향은 언제나 허용목록

두 공백의 교훈이 합쳐진 설계 규칙: `if:`를 **차단목록**(false를 쓰는 방법 열거)이
아니라 **허용목록**(정당한 조건 열거)으로 다룬다. false의 철자를 열거하는 것이
PR #402/#404를 세 번 패배시킨 바로 그 게임이다. 뮤테이션 테스트가 문자 그대로
false가 아닌 6개 조건을 고정한다: `${{ false }}`, `github.event_name == 'never'`,
`${{ 1 == 2 }}`, `${{ !always() }}`, `always() && false`,
`${{ github.actor == 'nobody-at-all' }}`.

`always()`는 목록에 있어서가 아니라 **의미상** 면제된다 — 앞선 실패 후에도 스텝을
강제 실행시키므로 무력화에 쓸 수 없다. 단, bare 형태만이다. `always() && X`는
무력화할 수 있고 탐지된다.

## 4.4 보론 — 사각지대에는 skip 계열만 있는 게 아니었다 (#412)

3.2절의 표는 실행이 못 보는 키를 나열하면서 전부 **스텝을 건너뛰는** 것으로만
분류했다. 새 체크리스트로 돌린 첫 감사가 그 분류가 불완전함을 보였다.

| 계열 | 키 | 결과 |
|---|---|---|
| **SKIP** | 스텝 `if:`, 스텝/잡 `continue-on-error:` | 스텝이 안 돌거나, 돌아도 종료코드가 버려진다 |
| **REDIRECT** | 스텝 `working-directory:`, `shell:`, 잡/워크플로 `defaults.run.*` | 스텝이 **돈다**. 성공을 보고한다. 그리고 **다른 것을 검사한다** |

실제 `security-scan.yml`의 게이트 스텝에 한 줄:

```yaml
working-directory: docs
```

**전체 스위트 1945개가 green인 채로** 필수 체크가 CRITICAL을 통과시켰다. 원리는
산술이다 — 게이트가 cwd 기준으로 `scan-output.txt`를 grep하고, 없는 파일에 대한
grep은 `|| true`가 삼키고, `CRITS`가 빈 문자열이 되고, `[ "" -gt 0 ]`은 에러가
나지만 **조건문의 실패는 `bash -e`가 의도적으로 치명적으로 다루지 않는다.**
`exit 1`이 실행되지 않는다. 추론이 아니라 실행으로 확인했다:

```console
cwd = repo root  ->  Critical: 1  ->  exit 1   (차단)
cwd = docs/      ->  빈 카운트     ->  exit 0   (조용히 통과)
```

`shell: cat {0}`은 더 나쁘다 — 스크립트를 실행하는 대신 **출력**하고 exit 0.

REDIRECT 계열이 SKIP보다 위험한 이유는 로그가 정상으로 보인다는 점이다. 건너뛴
스텝은 UI에 회색으로 표시되지만, 리디렉트된 스텝은 초록 체크가 붙는다.

> **"실행됐는가"와 "의도한 것을 실행했는가"는 다른 질문이고, 실행형 증명은
> 첫 번째만 답한다.**

## 4.5 보론 — 규모 추정은 세 번째로 틀렸다 (#413)

4.1과 4.2가 같은 실수의 두 방향이라고 썼다. 세 번째가 있었고, 이 회고를
쓰는 시점에 이미 레포에 있었다.

`test_ci_gate_topology.test_every_job_is_gated_or_allowlisted`는 "모든 잡이
애그리게이터에 물려 있어야 한다"를 **`lint.yml`에만** 적용하고 있었다. 필수
컨텍스트는 둘인데 하나만 검사한 것이다.

```console
security-scan.yml에 게이트 안 된 rogue 잡 (run: exit 1) 추가
  -> 1952 passed, 0 failed     영원히 실패해도 머지를 막지 않는데 아무도 모름
```

카탈로그 문서의 "Why two required checks matter" 절은 이 클래스가 토폴로지
가드에 의해 잡힌다고 명시한다. **두 워크플로 중 하나에 대해서만 참이었다.**

세 사례의 공통 형태가 이제 분명하다 — **가드의 스코프를 "지금 보고 있는 것"으로
잡았고, 실제 통제 경계는 그보다 넓었다.** 스텝 1개 vs 20잡 그래프, 레포 전체 vs
가드가 덮는 그래프, 파일 1개 vs 필수 컨텍스트 2개. 고침도 세 번 다 같다:
**세지 말고 유도하라** — `DESIRED_CONTEXTS`에서 스코프를 파생시키면 세 번째
필수 워크플로가 생겨도 그날 커버된다.

## 5. 주제 3 — 삭제도 결과다 (#406)

PR #406은 코드를 **192줄 지웠다**. 텍스트 기반 심각도 게이트 가드
(`test_ci_security_gate.conditional_body_from`)가 행동 테스트에 완전히 포섭되었기
때문이다.

전제 조건이 하나 있었다. 옛 텍스트 가드가 **유일하게** 커버하던 방향이 있었다 —
"HIGH는 WARN하고 exit 0"(#206 정책: CRITICAL만 머지를 막는다). 그 방향을 행동
테스트로 옮긴 **뒤에야** 삭제가 가능했다. 그 결과 `KNOWN_STRIP_ORDER_EXCEPTIONS`의
마지막 항목이 비었다.

부수 효과로 `test_ci_security_gate_behaviour.py`는 이 레포에서 유일하게
**뮤턴트가 게이트를 더 공격적으로 만드는** 자기검증을 갖게 됐다(HIGH에서도 차단).
통과하는 게이트만 보는 assertion은 실패하는 걸 보여줄 수 없기 때문이다.

## 6. 주제 4 — "증거 없음"과 "결함"은 파일할 때 구분되지 않는다 (#408)

PR #407 감사는 백로그 3건을 남겼고, #408이 정리했다. 그중 하나가
"뮤테이션 자기검증 없는 가드 3개"였다 — **프로세스 부채**로 분류된 항목이다.

셋 중 하나(`test_ci_npm_oidc_floor.py`)는 실제 false negative였다.

```yaml
run: npm install -g npm@'>=10.0.0'  # OIDC floor is 11.5.1
```

`npm@latest`가 아니고, `11.5.1`을 **포함한다**. 전체 줄 주석만 제거하는
스트리퍼는 이 줄을 통과시킨다. OIDC 트러스티드 퍼블리싱 요구치보다 메이저 하나
아래로 핀을 내려도 가드는 green이고, 실패는 런타임 publish에서만 드러난다.

> **아무도 실패하는 걸 본 적 없는 assertion은 약한 증거가 아니라 증거가 아니다.**
> 어느 쪽인지 알아내는 방법은 하나뿐이다 — 변형시켜 보는 것.

같은 절에서 하나 더. `test_ci_lighthouse_perf_gate.py`는 2026-07-28 분기 감사에서
**CLEAN으로 명시 판정**됐다("주석 회피 클래스가 구조상 해당 없음 — strict
`json.loads`"). 그 판정은 **그 감사가 훑던 클래스에 대해서는 정확했다.**
문제는 그게 "clean"으로 읽힌다는 것이다.

> **한 클래스에 대한 clean 판정은 그 스코프를 붙여서 기록해야 한다.**

## 7. 반복 가능한 체크리스트

이번 3사이클에서 실제로 값을 만든 질문들만 남긴다.

1. **실행형 증명을 썼다면**: 실행된 프로세스가 볼 수 **없는** 텍스트를 나열하라.
   그 목록이 남은 공격 표면이다.
2. **필수 체크를 다룬다면**: 그 체크 하나가 아니라 `needs:` 전이 폐포를 대상으로
   잡아라. 애그리게이터는 그래프의 결론을 받는다.
3. **"흔하다/드물다"로 범위를 정하려 하면**: 모집단을 명시하고 세어라. 1분이면
   되고, 뒤집힐 수 있다.
4. **무력화 형태를 다룬다면**: 차단목록이 아니라 허용목록. false의 철자는 무한하고
   정당한 조건은 유한하다.
5. **가드를 추가/수정했다면**: 실제 파일을 변형해 실행하고 **실패를 눈으로 봐라.**
   자기검증 없는 assertion은 항상 `[]`를 반환하는 detector와 구분되지 않는다.
6. **가드를 clean으로 판정한다면**: 어떤 클래스에 대한 clean인지 함께 적어라.
7. **감사 백로그를 "프로세스 부채"로 분류했다면**: 그 분류를 신뢰하지 마라.
   #408의 3건 중 1건은 결함이었다.
8. **공유 primitive가 있는데 손으로 다시 썼다면**: 그게 #391/#393/#394의
   메커니즘이다. 복사본은 각자 다르게 낡는다. 실제로 그랬다 — 감사 후속에서
   `test_ci_security_gate.gate_block_from`이 인용된 sibling job에서 `if:
   always()`를 빌려오는 것이 증명됐다(공유 `job_block`은 이미 그 클래스를
   막고 있었다).
9. **"GAP"이라는 판정을 믿기 전에, 뮤테이션이 통제를 실제로 무력화하는지
   먼저 증명하라.** 이 감사에서 probe가 **다섯 번** 틀렸다가 맞았다: `case`
   arm을 `*)` 바로 앞에 배치(여전히 도달 가능), 섹션 헤더만 수정, 파일 끝
   잡만 케이스로 잡음, 게이트의 **주석**에 든 `if: always()` 문자열을 지우지
   않음, `setUpClass`가 주입한 텍스트를 덮어씀. 다섯 번 다 이미 올바른 가드를
   "고칠" 뻔했다. 네 번째는 특히 시사적이다 — 이 레포가 가드에서 계속 잡아온
   주석 회피 클래스가, 이번엔 내 픽스처를 물었다.
10. **교체가 동등한지는 happy path로 판정하지 마라.** `gate_block_from`을
    공유 `job_block`으로 바꿀 때 파싱된 `needs:` 집합이 동일한 것만 확인했고,
    라인별 인라인 주석 제거(F-5b)가 빠진 것을 테스트가 즉시 잡았다.
